### 2. Locked business rules

This section records the decisions already established:

- rows are category-table based
- two definition types:
  - `superadmin_defined`
  - `user_defined`
- two row policies:
  - `fixed`
  - `addable`
- one child profile points to one parent segment + one parent category
- one child common field maps to one parent field only
- one parent field may feed multiple child fields in different segments
- common/generated rows use immutable backend row keys
- source-row removal auto-removes generated child rows
- categories without a profile keep current behavior unchanged

### 2.1 Conditional common-field extension rules

This subsection records the locked logic for adding `conditional` field support into the Common Fixed Rows module without disturbing the already-tested non-conditional flow.

- `conditional` is treated as one logical grouped block with two columns inside it:
  - primary field
  - secondary field
- one common-field segment may contain more than one independent conditional pair
- a common-field segment may mix conditional pairs with other supported common-field types
- if primary is blank, secondary may remain blank
- if primary has a value, secondary must also have a valid corresponding value
- if primary changes, secondary must auto-clear when it is no longer valid
- user-defined propagation must carry both primary and secondary together
- user-defined propagation works only one level down:
  - one mother may have multiple child segments
  - one child cannot become mother of another child
- propagated child-row identity should be tracked by:
  - mother row id
  - target segment id
- fixed profiles:
  - no manual extra rows
  - if mother adds a row, child auto-grows
  - if mother removes a row, matching child row disappears
- addable profiles:
  - propagated/admin-defined rows appear first
  - user-added extra rows appear below them
  - duplicate primary-secondary pairs are allowed
  - duplicate checking stays out of scope for now
- admin-defined conditional rows:
  - are entered by superadmin as paired primary-secondary values
  - may repeat for different office scopes
  - must use the same dependent-dropdown behavior as the current normal UI
- conditional Excel behavior must follow the existing system-generated conditional-template logic:
  - primary column first
  - secondary column next
  - secondary validation depends on primary value in the same row
- fixed common-field Excel:
  - predefined rows stay locked
  - extra rows stay locked
- addable common-field Excel:
  - predefined rows stay locked where required
  - additional blank rows remain available for entry
- audit modal must validate conditional pairs together:
  - if primary is present, secondary cannot stay blank
  - if mismatch appears, secondary should reset blank and require correction
- existing saved conditional values remain as legacy if the active option list later changes
- removed legacy options:
  - still display in existing saved rows, exports, downloads, and filters
  - must not appear as selectable for new entry
- recommended safety rule for deleting/editing conditional definitions already used in saved data:
  - existing rows keep legacy values
  - future use should be blocked by inactivation rather than destructive removal

## Manual Test Roadmap

Use this section as the acceptance checklist for the full Common Fixed Rows module. Each step includes the expected visible result so the behavior can be matched exactly.

### Test Set 1: Profile configuration at Management page

#### 1.1 Create a `superadmin_defined` common-row field

Steps:

1. Open `Management`.
2. Select a segment.
3. In one category, create or edit a field.
4. Enable `Common fixed-row field`.
5. Set:
   - `Profile Category` = that category
   - `Definition Mode` = `Superadmin Defined`
   - `Row Policy` = `Fixed`
6. Save.

Expected outcome:

- field saves successfully
- category appears in the `Common Row Profiles Summary`
- definition mode shows `Superadmin Defined`
- row policy shows `Fixed`
- bound field list shows the saved field label
- no parent segment/category/field is required for this mode

#### 1.2 Bind multiple fields into the same `superadmin_defined` profile

Steps:

1. In the same category, edit another supported field.
2. Enable `Common fixed-row field`.
3. Select the same `Profile Category`.
4. Keep `Definition Mode = Superadmin Defined`.
5. Save.

Expected outcome:

- no second separate profile is created for that category
- the same category profile now lists both field labels in the summary
- in `Superadmin Defined Common Rows`, the row table for that category shows both fields as separate columns
- this confirms one fixed row can hold multi-column values together

#### 1.3 Create a `user_defined` child field

Steps:

1. In a child segment/category, edit one supported field.
2. Enable `Common fixed-row field`.
3. Set:
   - `Definition Mode` = `User Defined`
   - `Row Policy` = `Fixed` or `Addable`
   - `Parent Segment`
   - `Parent Category`
   - `Parent Field`
4. Save.

Expected outcome:

- field saves successfully
- summary row shows parent segment and parent category
- bound field list includes the child field
- this child field is now linked to the selected parent field

## Final Acceptance Criteria

The module should be considered ready for broader use only if all of the following are true:

- one profile can define multiple bound columns in the same fixed row
- superadmin-defined row sets can be:
  - global
  - office scoped
- office-scoped rows override global rows only for that exact office
- global rows still work as fallback
- fixed/addable behavior matches policy exactly
- user-defined propagation is stable on add, edit, and delete
- autogenerated user templates round-trip without duplicate row creation
- superadmin row templates export and import correctly
- generated rows remain locked where required
- history is written for generated-row lifecycle
- no duplicate generated rows appear after repeated sync operations
- superadmin row-definition model
- materialized-row model in normal assets
- management UI additions
- user-side behavioral changes

It is decision-complete enough that implementation does not require new design choices.
