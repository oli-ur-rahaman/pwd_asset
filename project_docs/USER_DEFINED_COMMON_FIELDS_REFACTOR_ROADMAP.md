# User-Defined Common Fields Refactor Roadmap

Last updated: 2026-07-21

## Summary

Refactor `user_defined` common fields so they are no longer created manually from the normal field form. Instead, superadmin will declare inherited fields from a parent segment/field through a dedicated card placed before the `Asset Field` card. The system will auto-create and maintain the child fields from the parent definition, including conditional primary-secondary pairs, label/type/options sync, and propagation into child-segment rows.

`superadmin_defined` common fields keep their current behavior and remain controlled by the existing `Common fixed-row field` checkbox plus the `Common Fields` page.

## Finalized Product Rules

- `user_defined` common fields are declared from a dedicated superadmin card, not from the normal field form.
- One parent field may be reused in multiple child segments.
- A child segment may contain:
  - inherited `user_defined` fields
  - normal manually created fields
- Parent label/type/options/rules auto-sync to child.
- Child and normal fields share one unified order space.
- Conditional inherited fields are handled as one logical declaration block but two real fields.
- Parent field deletion is hard-blocked while inherited child bindings exist.
- Removing an inherited binding is hard-blocked once dependent child data exists.
- Parent field type change:
  - allowed for fixed child profiles
  - allowed for addable child profiles only if no user-entered manual child data exists for that inherited field
  - otherwise blocked with a popup reason
- `Common fixed-row field` checkbox is reserved for `superadmin_defined` common fields only.

## Phase Tasks

### Phase 1. Foundation and safety guards

- Add helpers to distinguish:
  - normal fields
  - inherited `user_defined` child fields
  - `superadmin_defined` common fields
- Add dependency queries for:
  - inherited bindings by child field
  - inherited children by parent field
  - conditional inherited declaration pairs
  - dependent child data existence checks
- Add hard-block rules for:
  - parent delete while inherited children exist
  - inherited-binding removal while dependent child data exists
  - parent type change when addable child manual data exists
- Keep current runtime behavior unchanged except for these new guards.

### Phase 2. Management UI refactor

- Add `Declare User Defined Common Fields` card before `Asset Field`.
- Provide:
  - parent segment selector
  - parent field selector
  - child sequence input
  - row policy selector: `fixed` / `addable`
  - declared inherited-fields table with remove/reorder actions
- Remove `user_defined` declaration responsibility from the normal field form.
- Narrow `Common fixed-row field` checkbox behavior to `superadmin_defined`.

### Phase 3. Auto child-field materialization

- On save of inherited declaration:
  - auto-create child `asset_fields`
  - copy label/type/options/rules from parent
  - mark child field as inherited `user_defined`
- For conditional parent:
  - auto-create both primary and secondary child fields
  - preserve pairing metadata
- Ensure inherited child fields appear in the unified sort order.

### Phase 4. Parent-child sync rules

- When parent label changes, auto-update child label.
- When parent options/rules change, auto-update child field definition.
- When parent type changes:
  - sync child type too when allowed
  - block when addable child manual data already exists
- Show explicit popup reasons for blocked actions.

### Phase 5. User UI / board behavior

- Ensure inherited child fields render by their true synced type in:
  - table
  - add modal
  - edit modal
- Fixed child profiles:
  - no manual add row
- Addable child profiles:
  - generated rows plus manual rows
  - manual rows use inherited child type correctly

### Phase 6. Template and bulk-import alignment

- Ensure autogenerated templates for inherited child segments use inherited field types correctly.
- Ensure conditional inherited fields generate proper conditional validation in Excel.
- Ensure bulk audit and save logic work correctly for:
  - `user_defined` fixed
  - `user_defined` addable
- Keep current `superadmin_defined` import behavior unchanged.

### Phase 7. Existing-data compatibility

- Detect current `user_defined` records built by the old field-form flow.
- Convert or bridge them into the new inherited model without data loss.
- Preserve already propagated child rows and existing parent data.

### Phase 8. Verification and rollout notes

- Update existing common-field documentation to mark the old `user_defined` flow superseded.
- Add deployment notes for:
  - new guards
  - compatibility bridge or migration
  - operator-visible behavior changes

## Testing Plan

### Declaration and creation

1. Declare one parent `text` field into a child segment as `user_defined` fixed.
   - Expected: child field is auto-created with parent label/type and appears in unified order.
2. Declare one parent `dropdown` field into a child addable segment.
   - Expected: child field is dropdown, and addable manual rows use dropdown UI.
3. Declare one parent conditional field pair into a child fixed segment.
   - Expected: both primary and secondary child fields are created and paired correctly.

### Propagation and backfill

4. Enter parent data before declaring inherited child field, then declare it later.
   - Expected: existing parent data backfills into child-segment rows.
5. Enter parent data after inherited binding exists.
   - Expected: child rows create/update correctly.
6. Reuse the same parent field in multiple child segments.
   - Expected: each child segment gets its own correct propagated rows.

### Fixed/addable behavior

7. `user_defined` fixed child segment.
   - Expected: no manual add row; generated rows only.
8. `user_defined` addable child segment.
   - Expected: generated rows appear; extra manual rows allowed and validated by inherited type.

### Conditional behavior

9. Inherited conditional pair in add/edit UI.
   - Expected: secondary depends on primary; if primary has value then secondary is required.
10. Inherited conditional pair in Excel template and bulk audit.
    - Expected: valid pair passes; mismatched pair is rejected.

### Blocking rules

11. Delete parent field used by inherited child bindings.
    - Expected: blocked, with dependent child segment/field message.
12. Remove inherited binding after child data exists.
    - Expected: blocked, with dependent data message.
13. Change parent field type when addable child segment has user-entered manual child data.
    - Expected: blocked, with reason popup.
14. Change parent field type when no user-entered manual addable child data exists.
    - Expected: allowed; child type syncs too.

### Regression

15. `superadmin_defined` common fields workflow.
    - Expected: unchanged.
16. Normal non-common segments.
    - Expected: unchanged.
17. Existing templates and bulk import for `superadmin_defined`.
    - Expected: unchanged.
18. Old `user_defined` configuration after compatibility bridge/migration.
    - Expected: still renders and syncs correctly.

## Acceptance Notes

- Do not remove or break the current `superadmin_defined` page/workflow.
- Do not silently mutate live child data when a blocked parent action is attempted.
- Prefer additive changes first, then switch UI ownership of `user_defined` flow after the new path is fully wired.
